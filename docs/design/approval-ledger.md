## 目標

## ラウンド3: アム Chat の回答 (APPROVAL-R2-53) を反映した、統合版 (v3)
アムの結論: 「現時点で自動実行への移行は未承認。設計と隔離テストを先行すること」。ラウンド2の表は、次の統合版で置き換える。

### v3 の仕組み
1. **型つきの承認スキーマ (版つき)**: 欄は、許可ID・環境識別子 (リポジトリ名と環境名)・目的・対象・操作・手順の列挙 (special のみ)・依頼の期限 (`+09:00` つき) ・スキーマ版。操作は、台帳の許可リストの名前だけ。対象は、台帳に登録されたものだけ。**曖昧な語・知らない欄・空欄は、拒否**。
2. **許可の1文は、検証済みのスキーマからだけ作る**。文字の正規化 (Unicode 正規化 NFC・改行 LF・前後の空白の除去・連続空白の固定) を、仕様で固定する。生成側と検証側は、**別々の実装**にして、同じ見本 (ゴールデンデータ) と、わざと壊した見本で、それぞれ試験する。一致は「本人が送った」証明ではない (共用アカウントの限界。2026-11-13 に、よしひろさんが受け入れた危険)。
3. **使用の予約は、受付が行う**。使用台帳の正本は、**受付 Bot の記録** (`[AMONE-ROUTED]` に、許可IDとハッシュを入れる。Bot の投稿は、所有者のコメントと区別できる)。`docs/special-used.md` は、人が読む要約。受付は、同じ PR の中で**直列に動く** (`concurrency` の設定。同じ PR では、同時に2つ動かない) ので、「許可IDが未使用か」の確認と予約は、分けても二重にならない。同じ許可IDで、別の依頼IDの予約が既にあれば、断る。失敗後の解放・再実行は、`docs/work-ops/special.md` の出し直しの決まりだけ。
4. **版の固定**: 台帳に、Work の指示文の期待する版 (例: W2) と、手順書の版 (コミットの印) を置く。依頼に、それを書かせる。**受付が、Work に渡す前に**照合する。Work は、起動時と、**変更を伴う操作の直前**にも、自分の版・手順書の版・承認を照合する。合わなければ、止まる。
5. **承認の検証**: 承認コメントを、コメントIDで直接取る。リポジトリ・PR・投稿者 (所有者の口座ID)・本文・時刻を検証する。取得できない・消えている・書き換えられている (ハッシュが違う) ときは、止まる。承認のコメントIDが、依頼より小さいことは、**補助**の確認にすぎない。
6. **承認の取り消し**: `[MONE-APPROVAL-REVOKE]` を置くと、その許可IDは無効。受付と Work が、変更を伴う操作の直前に確かめる。
7. **特例 (special)**: 列挙した手順でも、お金・認証・秘密・コード変更・Merge・範囲の拡大は、**列挙されていても拒否** (全権の限界)。
8. **お金**: 事前に「費用0円」と確定できない操作は、**台帳に入れない**。操作ごとに、手順書へ「費用0円の根拠」を書く。費用の確認画面が出ない従量課金や外部 API は、特に注意。分からないときは、実行しない。
9. **期限**: 起動時と、変更を伴う操作の直前の、両方で確認。時刻は、GitHub のコメントの時刻を基準にし、時計のずれ・タイムゾーン・日付の境目を試験する。
10. **途中の成功・結果不明**: 一部だけ成功したら、そこで止まり、実際に終わった手順を報告する。結果が不明なときは、再実行しない。再開は、**終わった手順を除いた、新しい依頼**だけ。
11. **記録**: 使うたびに、対象・操作・結果を `[AMU-RESULT]` に書く。秘密らしい文字列 (鍵・URL・メールの形) が出たら、書かない (検出して伏せる)。失敗が2回続いたら、止めて、未停止なら「未停止」と表示する。遅れて届いた古いイベントは、依頼IDの重複確認で何もしない。
12. **実行する側の権限を小さく**: Work が使える操作は、手順書にある操作名だけ。外部への送信先は、台帳に登録した宛先だけ。

### 切り替えの順序 (アムの案を採用)
1. 旧い経路を止める (**Work の凍結が、すでに効いている**)。
2. 新しい受付を、**検証だけのモード**で置く (予約・Work への受け渡しをしない)。
3. 新しい Work の指示文 (W2) を、凍結のまま設定する。
4. 受付と Work の、版・契約・実装の印・試験が、すべて一致することを確認する。
5. 新しい経路だけを有効にする (凍結を、`docs/approval-policy.md` の条件で外す)。
6. 切り替えの間は、旧新どちらも、副作用を起こさない。**戻すときも、旧い承認を、自動で再利用しない** (切り替え時に、既存の承認をすべて失効させ、新しい許可を取り直す)。
Work が旧い版 (W1) のままだと、W1 は「直接承認が要る」ので、新しい依頼を受けても、これまでどおり止まる。つまり、旧新どちらの組み合わせでも、**今より緩くならない** (安全側に止まる)。

### 試験の計画 (実装の前に作る。テスト係が書く)
- 承認スキーマ: 正しい例、操作名が許可リストにない、対象が未登録、知らない欄、空欄、曖昧な語、期限の形式違い (`+09:00` なし)、環境識別子の違い。
- 許可の1文: 見本と一字一句一致、全角半角・改行・空白の揺れ、生成側と検証側の食い違い。
- 予約: 同じ許可IDで別の依頼、別の許可IDで同じ依頼、並行して届いた2件、失敗後の出し直し1回、期限切れ、取り消し後。
- 承認コメント: 編集された、消された、別の PR のもの、所有者でない投稿者、依頼より後のもの。
- 版: 期待と違う指示文の版、手順書の版、承認の取り消し (実行の直前)。
- 特例: 禁止操作を列挙した、列挙にない手順、範囲が書けない。
- お金・秘密: 費用の言葉、URL・鍵らしい文字列、費用0円の根拠がない操作。
- 実行の途中: 部分成功の報告、結果不明のあとの再実行の拒否。

## ラウンド4: アム Chat の回答 (APPROVAL-R3-54) を反映した、v4
アムの結論: 「設計検討は継続可。ただし、予約の原子性・旧経路の完全停止・実行側の版照合を証明するまでは、新経路の有効化は不可」。v3 の次の点を、v4 で置き換える。

### v4 の変更
1. **予約の正本を、「Git のタグ」に移す (コメントではない)**。許可IDごとに、タグ `approval/<環境識別子>/<許可ID>` を**作る**ことが、予約。同じ名前のタグは、2つ作れない (GitHub がサーバー側で拒否する) ので、「確認してから記録」の2段にならず、**作成の成否が、そのまま確認と予約を兼ねる**。競合したら、片方は失敗して止まる。タグには、注釈つきタグの本文として、依頼ID・承認の本文のハッシュ・受付の時刻 (受付が取った GitHub の時刻) を入れる (あとから書き換えられない Git の記録)。`[AMONE-ROUTED]` のコメントは、**結果の通知だけ**。concurrency の設定は、補助であり、保証とは見なさない。
   - **許可IDは、環境識別子つきで、1つの正本の中で一意**にする (許可の1文に、環境識別子を入れる。別の環境・別の PR に、使い回せない)。
   - 必要な権限: 受付の `contents: write` (タグの作成のため。いまは read)。**権限が広がる変更なので、よしひろさんが Merge する**。タグの削除・上書きを禁じる保護 (リポジトリの設定。公開リポジトリでは無料の見込みだが、**未確認**) が必要。
   - **原子性を実機で証明できなければ、予約機能は有効にしない** (D3)。そのときは、引用承認をやめ、これまでどおり直接承認 (案1) のまま。
2. **Work は、予約のタグを自分で読んでから動く**。起動時と、変更を伴う各手順の前に、タグ (依頼ID・ハッシュ) を読み、承認コメントのハッシュと照合する。タグがない・食い違う・読めない、なら止まる。→ **予約の記録の前に、Work が動くことは、できない**。チャットでよしひろさんが直接 Work に頼んだ場合も、同じ (タグがなければ、副作用を起こさない)。
3. **旧い経路の洗い出し (切り替えの前提)**: Work に仕事が届く経路を、全部、台帳に書き出す: (a) 受付 (PR #25 のコメント)、(b) Work のチャットでの直接の指示、(c) 古い予定タスク (「新」の前のもの) が残っていないか、(d) ほかの予定タスク。それぞれ「止まっている」ことを、よしひろさんの画面で確認する。1つでも未確認なら、切り替えない。
4. **旧い承認の失効**: 切り替えの時点で、既存の承認 (引用を含む) をすべて失効させ、新しい書式で取り直す。ロールバックのときも、旧い承認は使わない (D4: 取り直しの手間は、よしひろさんの判断)。
5. **時刻**: 期限の比較に使う時刻は、受付が API の応答から取る GitHub の時刻 (タグの本文に記録) を基準にする。Work 側の時計は信用しきれないので、**期限の5分前を過ぎたら、新しい変更を始めない**。コメントの作成時刻は、現在時刻の代わりにしない。
6. **結果は、構造化した出力だけ**: `[AMU-RESULT]` は、許可した項目 (状態・終わった手順の番号・理由の分類コード・次の担当) だけ。自由な文章は、短い定型の理由に限り、URL・鍵らしい文字列を「伏せる」のではなく、**書く項目を最初から持たない**。
7. **実行の途中の確認**: 複数の手順の間は、手順ごとに、取り消し・期限・版を確認する。**不可逆な外部操作** (公開・削除など) は、確認と実行の間に取り消しが入る、わずかな隙間が残る。完全な排他はできないため、**残る危険として明記し、その操作は小さく・1手順ずつ**にする (D5)。
8. **お金**: 追加の費用が0円と確定しない仕組みは、候補から外す。タグの作成・保護は無料の見込みだが、公開リポジトリの設定の無料枠は、**実装の前に確認する (未確認)**。確認できなければ、そこで止まり、よしひろさんに聞く。

### v5 で変える点
1. **予約 (タグ) は、「予約の獲得」だけを示す**。「実行が一度きり」は、保証しない。
   - 作成は、「同じ名前がないときだけ作れる」API (作成のみ。更新・上書きは使わない) で行い、**競合の試験で確認する**。タグの実体と参照の作成が別操作になること、途中の成功・応答の喪失を、区別する。予約が成功して通知だけ失敗したら、「予約済み・未実行」と判定し、同じ許可IDで新しく予約しない。結果不明なら、タグと記録を読み直し、不明のままなら止まる。
   - タグの削除・付け替えを防ぐ保護の規則を、**実機で確かめる** (管理者・Bot の迂回を含む)。確かめられなければ、予約機能は有効にしない。
   - `contents: write` はタグ専用の権限ではない。**専用の隔離したリポジトリ**で、最小の権限・規則・監査を、先に検討する。
2. **実行の一度きり**は、別の仕組みで守る: 依頼ごとの実行状態 (未着手 → 実行中 → 完了) を、条件つきで1回だけ進められる形にする。GUI を使う Work では、完全な保証が難しいので、**「冪等な操作」だけを引用承認の対象にする**: 操作の前に、外部の現状を確かめ (すでに作られていないか)、操作のあとに、結果を照合する。**冪等にできない・取り消せない操作 (公開・削除・本番の変更) は、引用だけで進めない**。対象ごとの直接承認 (従来の案1) を残す (アムの推奨に従う)。
3. **経路の洗い出し**は、v4 の4つに加えて、手動の起動・既に実行待ちのもの・再試行・別のチャット・ショートカット・外部連携・GitHub Actions の別の workflow や手動の実行、を数える。**順序: 旧経路の無効化 → 実行待ちの解消 → 新方式の隔離試験 → 切り替え**。全経路を1つにそろえられないなら、**副作用のある引用承認は、有効にしない**。
4. **時刻**: API の応答の時刻 (Date ヘッダー) は、原子的な証明ではない。**5分の余裕は、安全の保証ではない**。期限・取り消しは、**副作用の直前**に必ず確かめ、時刻が分からない・取得できないなら停止する。期限切れのあとの再開は、しない。
5. **結果の出力**: 項目ごとに、型・長さ・決まった値・改行や制御文字なし・自由な文字列なし、を検証する。理由は、固定のコードだけ。外部の本文・例外の文面・ハッシュ・URL を、結果に混ぜない。Actions の自動のログにも、秘密が出ないことを確かめる。
6. **合格の条件 (失敗を注入する試験)**: 「二重の副作用ゼロ」「権限外の副作用ゼロ」「不明なときは停止」。新しい故障の型も、試験に入れる: 予約のあとの承認の取り消し、タグだけ作成が成功、タグの付け替え、タグの参照先と承認本文の不一致、旧い Work がタグの検証を迂回、実行中の停止、別環境での二重実行、保護設定の不備。
