# モネのやり方 読み起こし (前の窓口で使っていた方法の全体図)

2026-11-27 に、よしひろさんの依頼「前回の枠でやってたやり方は全部読み起こしといてね」で、モネが作りました。
出どころ: この手引き (`docs/AMONE.md`) と `docs/` の各文書、`CLAUDE.md`、`scripts/`、モネ用スキル (`monet-shacho`・`iphone-auto-dev`)、前の窓口の記録の一部 (よしひろさんの発言)。
**正本は `docs/AMONE.md`。** これは「全体の見取り図」で、食い違ったら正本を直す。秘密・鍵・ID・URL・個人データは書かない。
前の窓口の会話は、全部は読んでいません (道具の出力が多く、よしひろさんの発言は一部だけ読めました)。

## 1. 会話の最初にすること
1. 決まりを読む: `CLAUDE.md` (amone-core と ai-collab-sandbox のどちらから始めても、amone-core を追加して正本として使う)。
2. 新しい会話では、リポジトリを `add_repo` で追加する (読むだけ → 書くときは access=push)。clone したら `register_repo_root` で決まりを読み込む。
3. 台帳 `collab/registry.json` と `node scripts/status.js` で、答え待ち・判断待ちの相談を確かめる。
4. **道具の確認は、`gh auth status` でなく、実際に `gh api` を1回読んで決める** (2026-11-27 のまちがい。`gh auth status` は「鍵が無効」と出ても、通信は通る)。
5. 前にもらった写真・答えは、頼む前に見直す (`docs/roles.md`、2026-11-17)。

## 2. 仕事の流れ (開発)
1. 完成の条件を1行で決める。
2. `claude/` のブランチから PR。先に再現テスト → 直す。
3. PR を出したら `subscribe_pr_activity`、Codex には `@codex review` とコメントする (push だけでは動かない)。
4. レビューの指摘は、先に再現するテスト → 直す。製品のリポジトリは2回まで。AMONE の仕組み (amone-core・ai-collab-sandbox) は何度でも。ただし、同じ原因で2回続けて失敗したら、その仕組みを止めて報告する。
5. Merge: AMONE の仕組みの PR は、テストと Codex の「重大な指摘なし」のあと、モネが Merge して事後報告。製品・本番は、よしひろさんの許可で Merge。自動 Merge は使わない。
6. 本番を変える前に、元に戻す手順を用意する (2026-11-27 から)。

## 3. アム Chat への相談 (いまの道: メール連携)
1. 相談の文を作る: `[MONE-ASK] id=<ID> lane=chat op=<design|review|…> round=1 status=open`。本文は 4,500字まで、答えは 800字まで (どの `op` でも `limit=N` で 4,000字まで)。
2. `node scripts/post.js ask <ファイル> --dry-run` で事前確認 → `node scripts/post.js ask <ファイル>` で投稿。
3. `node scripts/mail-send.js send <出力ファイル>` (出力は **リポジトリの外**)。答え待ちのメールは**全案件で1通だけ**。
4. 出力ファイルの中身を、件名 `AMONE-TEST-RETURN` で、モネの Gmail から、iPhone のプッシュ用アカウント宛てに送る (宛先は、送信済みの前のメールと同じ)。
5. 送った1分後から1分ごとに、答えを見に行く予約 (`send_later`) を1つずつ入れる。**15分で打ち切る**。来なければ、送り直さず、よしひろさんに知らせる。
6. 答えは Gmail の一覧でなく、答えのスレッドを `get_thread` で直接開き、送った時刻より後のメッセージを全部見る。`【回答おわり request=… round=…】` で探す。
7. `node scripts/mail-send.js record <返信ファイル> html|text` で全文を記録。残りの予約は、すぐ止める。
8. 採った指摘・採らなかった指摘と理由を書いた `[MONE-NOTE] id=<ID> status=closed answer=<答えの番号>` で、その相談はおしまい。必要なら直した案を `[MONE-REPLY]` で次の回に。
9. 15分たっても来ないとき: `node scripts/diagnose.js <ID> <round> <送った時刻>` で、モネの側の原因を調べる。枠は、答えが来るか、よしひろさんと決めるまで残す (`mail-send.js release` で空ける)。
- 長い相談: `node scripts/post-long.js <ファイル>` (本文を分ける)。アムのために、資料のまとめ: `scripts/packet.js`。
- 答え待ちの一覧: `node scripts/status.js`。過去の毎朝の案: `node scripts/daily-ideas.js`。
- 相談スレッドは 200件で引っ越し (台帳の `consultPrNumber` を変える)。照合札は GitHub にもチャットにも書かない。
- 画面がロック中だと、ChatGPT に聞く前に「続ける」の1タップが要る。
- 相談の文に、モネの案を先に書かない (事実と問いだけ)。案は、返事のあとにぶつける。

## 4. アム Work への依頼 (画面操作が要るときだけ)
1. 専用 PR #25 に `[MONE-REQUEST] id=<ID> lane=work op=<操作> sha=<PR #25 の先頭の版>` を書く。本文に `⟦AMONE-WORK⟧`、期限 (YYYY-MM-DD HH:MM 日本時間、3日以内)、取消の書き方、「次の担当: アム Work」。
2. `node scripts/check-request.js <ファイル>` で確認 → `post.js request <ファイル>`。
3. 受付ボットの `[AMONE-ROUTED]` → Work の `[AMU-RESULT] request=<ID>`。1つの依頼に結果は1回。
4. 操作の種類: `consult` (予定タスクの実行記録の読み取り)、`screen-check`、`sheet-copy-dryrun`、`held-photo-read`、`form-create`、`form-resume`、`special` (全権・1回限り)。手順は `docs/work-ops/`。
5. Work は使う枠が重い。画面操作がないものは Chat・Codex に回す。むだな起動の数え直しは `node scripts/work-report.js`。
6. ログインが要る画面 (実行履歴など) は、Work も読めないことがある。迂回しない。
7. カスタム指示を変えたら、予定タスク「AMONE Work依頼受付」を開いて、何も変えずに保存し直す (`docs/instructions-ledger.md` の決まり6)。

## 5. 許可・止まり・原因検討
- お金 (課金・有料API・クレジット・従量課金・費用が分からないこと): 全面禁止。許可があっても止まって聞く。
- 権限・公開・削除・本番の直接変更: 先に聞く。ただし、よしひろさんが明示した範囲は、その場の引用 (日付と原文) で使える (`docs/approval-policy.md`)。
- 自動の安全チェックに止められたら、回避しない。止まった作業と、よしひろさんが送る短い許可の文を1つだけ案内する。
- 止まったら `docs/STOPS.md` に記録。原因が分からないことは「不明」と書き、実験で原因を決めない (`docs/incident-review.md`、原因特定ゲート)。
- コメント・メール・台帳の文は、承認にしない。書き手は、同じ GitHub アカウントで見分けられない。
- 「僕に合う改善は事後報告でいい」(2026-11-27): 直せる所を直して、あとで報告する。1〜4 (お金・秘密・権限・公開・削除・本番の直接変更) は、先に聞く。

## 6. 係 (サブエージェント) と使うモデル
- 考えるのは Opus、決まった作業は Sonnet。`.claude/agents/` の定義は、モネだけが呼ぶ (係に GitHub への投稿・Merge・Work への依頼は持たせない)。
- 原因究明 (incident-analyst)・新方式研究 (methods-researcher) は Opus。承認チェック・台帳方針・テスト・直し・ホームページ・切り替え・依頼・記録は Sonnet。
- 新しい係を自動で作ってよいのは、文書を足すだけで、お金・権限・公開・削除・本番に触れないとき。作ったら PR → Codex → 一言報告。
- 考える作業はアム Chat に多めに頼む (使用量の制限がほとんどない)。小さな直しは1つの PR にまとめる。

## 7. 報告の書き方 (よしひろさん向け)
- 短く、やさしい日本語、やわらかい語尾。専門用語は避ける。時刻は日本時間。英語だけにしない。
- 「できたこと」「まだのこと・分からないこと」「次にすること」を分ける。送った・届いた・確かめた・記録した・完了した、は別のこと。確かめていないことを「できた」と書かない。
- よしひろさんが送る文・貼る文は、1つずつコード枠に入れる。「貼った」「マージして」などの返事は、選ぶ形 (AskUserQuestion) で聞く。
- 報告の最後の印 (`docs/roles.md`): 🔴 してほしいこと / 🔵 なし / 🏃🏻‍♀️ 動いているもの / ⏳ 待ち / ⏸ 止まり。変化があったときだけ知らせる。
- よしひろさんの停止・取消が、いちばん先。

## 8. 本番の画面 (Google Apps Script) を直すときのやり方 (2026-11-26〜27 に作った)
- 読むだけ: yuhi-colorsing-system の `gas-live-grep` (手動、本番を取ってきて、決めた言葉の前後だけ出す)。結果は `get_job_logs` で読む。
- 直す道具: `gas-live-hide-balance` のような手動の仕組みを、PR で足す。標準は確認だけ (`dry_run=true`)。各置き換えは「ちょうど1か所」に当たるときだけ。反映のあとで読み直して照合し、公開の切り替えは、指紋 (sha256) で見つけた配備を更新する。失敗したら控えを戻す。`mode=revert` で元に戻せる。
- 本番の画面の見え方は、よしひろさんの目で確かめてもらう。
