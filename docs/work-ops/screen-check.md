# Work の操作 `screen-check` (読み取りだけの試験: 画面で状態を見て、結果を報告する)

目的 (2026-11-15、アム Chat の独立レビュー INC-WORK-57 の勧め): **報告のコメント以外の書き込みがない**試験で、「着手 → 実行 → 終了 → 結果の報告」の道が最後まで動くかを確かめる。

**状態: 有効 (2026-11-15、`docs/approval-policy.md` 第13版で決まった。最初の1件に使う)。**
**前提 (方針との関係)**: 原因特定ゲート (`docs/approval-policy.md` 第12版) の、よしひろさんによる例外として、**第13版で、sandbox の Work の凍結が、まるごと解除された** (原因は、いまも「未特定」。`docs/STOPS.md`)。この手順書は、解除の直後の、**最初の1件**の手順。
(順序: 第13版の Merge → 受付の固定先の更新の Merge → 解除が効いたことの確認 → この依頼。解除が効く前に出した依頼を、受付が断るのは、結果の欠落ではない。)

## 範囲 (これだけ)
- sandbox の PR #23 (相談スレッド) を、**読むだけ**で開き、(1) open か closed か、(2) コメントの件数、を画面で確かめる。
- **書き込みは、PR #25 への、手順で決められた報告のコメント (`[AMU-CLAIM]` と `[AMU-RESULT]`) だけ**。それ以外は、しない: PR #23 を含む、ほかの場所への、コメント・ラベル・レビューの投稿、設定・ファイルの変更、ほかの場所を開くこと、ログイン・認証の代行。費用が出る表示が出たら止まる。
- 承認は要らない (読み取りだけの操作)。

## 依頼の書き方 (モネが、sandbox の専用 PR #25 に書く)
```
[MONE-REQUEST] id=<ID> lane=work op=screen-check sha=<この依頼を書く PR の、いまの先頭の版>
⟦AMONE-WORK⟧
手順書の版: docs/work-ops/screen-check.md の amone-core main の版 (コミット)
目的: 凍結解除の直後の、読み取りだけの試験
開始の時刻: <日本時間>
最大の許容時間: 60分 (これを過ぎても結果がないときは、モネが止めて、よしひろさんに報告する)
報告: どんな状態で終わっても、[AMU-RESULT] request=<ID> を1回、GitHub に書く。画面にも必ず報告する
取消: [MONE-REQUEST] id=<ID> status=cancel があれば、何もせず止まる
次の担当: アム Work
```

## 手順 (Work)
0. 依頼の全項目、取消の有無、`sha=` が先頭の版と同じこと、既存の結果が無いことを確かめる。合わなければ、何も書かず終わる。
1. 最初に `[AMU-CLAIM] request=<ID>` を1回書く (着手の記録)。
2. PR #23 を読み取りで開き、open/closed とコメント件数を確かめる。
3. 終わったら、`[AMU-RESULT] request=<ID>` を1回書く。内容は、状態 (open/closed)・コメント件数・終了の時刻 (日本時間)・次の担当だけ。止まったときは、止まった理由の分類だけ。
4. 失敗したら、自動でやり直さない。

## モネの側の確認 (結果の欠落を見つける)
- 依頼を出したら、時刻を記録する。**15分後**と**60分後**に、PR #25 の `[AMU-CLAIM]` と `[AMU-RESULT]` を確認する。
- 15分の時点で結果がなくても、**失敗とは決めない** (進行中でありうる)。着手の記録 (`[AMU-CLAIM]`) があるかを見て、「着手あり・結果待ち」または「着手なし」と、よしひろさんに報告する。
- 60分を過ぎても結果がなければ、「結果欠落」として止まりとして記録し (`docs/STOPS.md`)、再実行せず、よしひろさんに報告する。自動の解除・再実行はしない (凍結は廃止された。`docs/approval-policy.md` 第14版)。
- この試験の結果が確認できるまで、`screen-check` 以外の依頼は、**モネが出さない** (台帳の凍結は外れているが、これは、モネの決まり)。

### 静かな読み取り試験(依頼に quiet=yes があるときだけ)
(アム Chat が WORK-CAUSE-4 で作った案。2026-11-16)
- **目的**: Work の結果が出ない原因の候補A (PR #25 への新しいコメントが同じ予定タスクの別の実行を起こし、動いている本体の邪魔をする) を見分けるため、実行中に PR #25 へ何も書かない試験を行う。試験は**依頼IDごとに1回**だけ実行し、同じIDで出し直さない。回数の上限は、よしひろさんの許可に従う (2026-11-16 の許可は最大10回、毎回やり方を改善してから次を出す)。結果が出ても、原因の証明にはならない (下の早見表で判断)。
- `quiet=yes` が無い依頼は、従来の手順 (着手の記録あり) を守る。
- `quiet=yes` の依頼では、上の「手順 (Work)」の**手順0と手順4はそのまま**行い、**手順1〜3の代わりに**、次の Q1〜Q3 を行う (手順1の着手の記録は書かない。手順2の PR #23 は開かない。手順3の報告の項目も、Q3 に置き換える)。手順0の照合 (依頼の全項目・取消・差替え・`sha=`・既存の結果)、台帳・許可範囲の照合は省かない。W1 と手順書のどちらかと矛盾があれば止まる。
  - Q1. 着手の記録を書かずに、下の4ページを順に、読むだけで開く。
  - Q2. 実際に表示を確かめたページ数、最後の操作、開始・終了の時刻 (実際に分かった値だけ。分からなければ「不明」) を記録する。
  - Q3. 終わる直前に、同じ依頼IDの取消・差替え・既存の結果と権限をもう一度確かめ、`[AMU-RESULT] request=<ID>` を PR #25 に**最大1回だけ**書く。内容は、表示を確かめたページ数・最後の操作・開始と終了の時刻・完了/停止の理由・次の担当だけ (PR #23 の状態やコメント件数は書かない)。
- 開くのは、sandbox (`ai-collab-sandbox`) の中の、次の閲覧だけのページに限る (順に開く): (1) リポジトリのトップ画面、(2) README のファイル表示、(3) コミットの一覧、(4) ブランチの一覧。PR #23・#25 の会話、コメント入力欄、Actions、設定、認証画面、外部サイトは開かない・操作しない。
- **記録**: 実際に表示を確かめたページ数、最後の操作、開始・終了の時刻 (実際に分かった値だけ。分からなければ「不明」)、完了/停止の理由。
- 終わる直前に、同じ依頼IDの取消・差替え・既存の結果と権限をもう一度確かめ、`[AMU-RESULT] request=<ID>` を PR #25 に**最大1回だけ**書く。途中で止まった・結果が不明なときは、再実行・再投稿しない。
- **注意**: 着手の記録が無いので、結果が無いことを「実行されなかった」と決めつけない。二重実行は無害ではない (使用量・重複投稿)。投稿直前の照合で抑えるが、完全には防げない。

結果の早見表:

| 結果 | 言える | 言えない |
|---|---|---|
| 結果が1件・時刻と件数と最終操作あり | 少なくとも結果が記録された | 閲覧の正確さ、重複起動がゼロ、原因の確定 |
| 結果が2件 | 重複投稿が起きた | 二重起動だけが原因 |
| 結果なし | 指定場所に結果が無い | 未起動・実行中・途中停止・時間切れの区別 |
| 停止の報告あり | その理由で報告された | 他の実行が残っていないこと |

**モネの側**: この試験は、よしひろさんがモネの会話で許可を出した回数の範囲でだけ依頼する (手順書としては承認不要の読み取りだが、モネの決まり)。依頼IDごとに1回。前の回の結果を確かめ、アムと相談してやり方を直してから次を出す。

#### 陽性対照 (依頼の目的に「陽性対照」と書いたときだけ)
- 静かな読み取り試験と同じ手順 (Q1〜Q3) で行う。違いは、モネが、画面確認の最中 (依頼の約60秒後) に、PR #25 へ、オーナー名義の連絡コメント `[MONE-NOTE] id=<依頼ID>` を**1件だけ**書くこと。
- その連絡コメントは依頼ではない。それで起きた Work の実行は、W1 のとおり、何も書かずに終わるのが正しい。本体は、その連絡コメントを理由に止まらず、Q1〜Q3 を続ける。
- 目的は、オーナー名義のコメントで起きた別の実行が、動いている本体を止めるかを見ること。本体が完了しても止まっても、それだけでは原因は確定しない (早見表で判断し、あとで Work に実行の一覧を聞く)。
